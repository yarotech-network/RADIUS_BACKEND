# 05 — Backend/API gaps that shape the frontend

These are things the UI would naturally want but the backend does **not** provide. The frontend will not fabricate them; each has a stated fallback. Items marked **(blocking-ish)** materially degrade a workflow and are worth a small backend follow-up.

| # | Gap | Evidence | Frontend handling |
|---|---|---|---|
| 1 | **Agents cannot list the plans they can buy.** `GET plans/` uses `tenant_for()` → agents (no membership/staff assignment) get 403. There is no `agent/plans/` endpoint and the agent login/profile payload contains no tenant slug. **(blocking-ish)** | `apps/vouchers/views.py::InternetPlanViewSet.get_queryset`, `apps/core/api.py::tenant_for`, `AgentProfileSerializer` (tenant is an id) | Agent "Sell" screen loads plans from the public catalogue `GET public/tenants/{slug}/plans/` **only if** a slug is known: the portal will accept `?tenant=<slug>` on the agent login URL / a "Your operator's storefront slug" field saved locally; otherwise it falls back to entering a plan ID manually with a clear message. Recommended backend fix: expose `tenant_slug` on `agents/me/` or add `GET agent/plans/`. *(Phase 7, implemented: `StoreLinkForm` + `useStoreSlug()`; the slug is verified against `public/tenants/<slug>/` and kept in `localStorage`. Confirmed live: `plans/` → 403 and `tenants/` → empty for the agent session; the public catalogue returns the same plans, and a plan from another tenant is rejected by `generate/` with a `plan_id` field error, which the Sell screen shows on the field.)* |
| 2 | **Generated voucher passwords are not returned by `vouchers/generate/`, `POST vouchers/`, or agent `generate/`.** `password` is write-only; credentials are only visible through `vouchers/{id}/print/` and `/pdf/` (manager/staff), and agents have **no** print/pdf permission. **(blocking-ish for agents)** | `VoucherSerializer.extra_kwargs`, `AgentVoucherAllocationSerializer`, `VoucherViewSet.get_permissions` (print/pdf need `IsAuthenticated` but the queryset is `tenant_for()` → 403 for agents) | Workspace: after generation, offer per-voucher "Print" (fetches HTML) and "Print all" (sequential fetches into one print document). Agent portal: show usernames and explain that credentials are printed by the operator; surface this gap prominently in docs. Recommended fix: return `password` in the generate responses (they are creation responses) or add an agent-scoped print endpoint. *(Phase 7: the agent Sell result and voucher list show usernames only, with copy/print actions and an explicit note that the operator issues passwords. Confirmed live: `vouchers/{id}/` and `/print/` → 403 for agents.)* **Resolved for new vouchers (backend PR "deliver the voucher access code after purchase"):** `Voucher.generate_credentials` now issues one 8-character access code used as both username and password, and `access_code` is returned by `vouchers/`, `vouchers/generate/`, agent `generate/` and `history/` (null for legacy or manual vouchers with a separate password, which remain print-only). The agent Sell result and voucher list show the code; the workspace voucher detail shows it with a copy action. |
| 3 | **No user directory / user search.** Team membership creation and staff-assignment creation require an existing **numeric user id**; there is no `GET users/`. | `TenantMembershipSerializer.user` is a PK field; no users endpoint in `openapi-v1.yaml` | Team → "Add member" asks for the user's ID with helper text ("Ask the user for the ID shown under Settings → General → Your account"). That card displays the user's ID with a copy button. *(Built in Phase 6.)* The "already exists" error also fires for users who belong to **another** tenant — one workspace per account. |
| 4 | **No invitation e-mail for staff invitations**; the token is returned once at creation. | `StaffInvitationViewSet.create` | Console shows a one-time "Copy invitation link" (`/accept-invitation?token=…`) with a warning that it cannot be retrieved later. |
| 5 | **Commission is never computed** (`commission_earned` stays 0; `agent_commission_percent` is unused by business logic). | `AgentService.generate_voucher_from_wallet` sets no commission; grep shows no writer | Agent stats show "Commission this month" only when >0; otherwise the card is omitted. Settings label the commission % as "recorded for reporting; not applied automatically". |
| 6 | **No time-series / trend data** (revenue by day, sessions over time, voucher usage). Only totals. | `DashboardStatsView`, `PlatformStatsView` | No charts. Dashboard uses stat cards + "needs attention" list + activity feed. |
| 7 | **No router telemetry**: `health.online` is always `null`, `telemetry_available:false`; `last_seen_at` only changes if `refresh_router_statuses` runs. | `RouterOperationActions.health` | Router health card shows "Telemetry not available"; `last_seen_at` shown as "Last seen (ping worker)" with staleness. | 8 | **Live sessions lack client IP / MAC** (`client_ip` always null) and there is **no usage/accounting history** endpoint (closed sessions, per-voucher usage). | `LiveUsersView` | Sessions screen shows only live sessions; voucher detail has no usage tab. |
| 9 | **Paystack return URL is not passed by the backend** (`callback_url` absent). Where the browser lands after payment depends on the Paystack dashboard configuration. | `PaystackService.initialize_transaction` | The frontend provides three return pages (`/pay/result`, `/agent/wallet/return`, `/settings/subscription`) that poll by `reference`; docs instruct the operator to configure Paystack's callback URL to `/pay/result` (Paystack appends `?reference=`). Agent/subscription flows also store the reference locally before redirecting so the return page can recover it. *(Phase 7: `/pay/result` and `/agent/wallet/return` also accept Paystack’s `trxref` parameter, and fall back to the reference remembered in `localStorage` (`yr.checkout.pending`) when no query string arrives; the entry is cleared once the payment settles.)* |
| 10 | ~~**Public purchase result never exposes credentials**; `payments/callback/` returns only the voucher username, and credential e-mail delivery is a manual operator command (`deliver/`).~~ **Resolved (backend PR "deliver the voucher access code after purchase").** Fulfilment now queues a `PaymentDelivery` automatically when the buyer left an email (sent through Resend when `RESEND_API_KEY` is set, otherwise Django's `EMAIL_BACKEND`), and `payments/callback/` returns `access_code` + `code_revealed` + `plan` + `tenant_name` + `customer_email_masked`. The code is revealed **only while the voucher is `unused`**, so a shared or logged reference stops being a usable credential after the first login. Legacy vouchers with a separate password are never revealed. | `PaymentCallbackView`, `apps/payments/recovery.py::queue_credential_delivery`, `apps/payments/delivery.py` | `/pay/result` shows the access code with copy + "How to connect" steps and notes the emailed copy (masked address); after first login it shows the username only and points at the email. The page still degrades to the pre-change shape (username only). Operators must run `process_payment_deliveries` on a 30–60 s schedule — the Recovery board's delivery column now reflects automatic deliveries too. |

| 23 | **Platform staff cannot resolve tenant names.** `GET staff/assignments/` returns tenant *ids*; `GET tenants/` for a staff user returns an empty page (queryset is membership-based), and `public/tenants/{slug}/` needs a slug. *(Confirmed against the running API during Phase 3.)* | `MyStaffAssignmentsViewSet`, `TenantViewSet.get_queryset` | Tenant picker / switcher show **“Tenant #id”**; the workspace header shows the same label. Recommended fix: add `tenant_name` (and `tenant_slug`) to `StaffAssignmentSerializer`. |

| 24 | **No `agent` filter on `vouchers/`.** `VoucherFilter.search` matches `username` *or* `agent__user__username` (icontains), so an agent's sales can only be approximated. *(Found in Phase 5.)* | `apps/vouchers/filters.py` | Agent detail → “Vouchers sold” queries `search=<agent username>` and keeps rows whose `agent === id` client-side; counts may be under-reported across pages. Recommended fix: add `agent = NumberFilter(field_name="agent_id")`. |
| 25 | `wallet_balance` on `tenant/agents/` is **`null`** for agents without a wallet row (created outside `AgentManagementViewSet.create`). *(Observed in the harness.)* | `AgentProfileSerializer` (`default=0` does not apply to `source="wallet.balance"` misses) | Typed as `Kobo \| null`; UI shows “No wallet yet” / “—”. |
| 26 | `router-operations/` is manager-only, so **read-only viewers cannot see whether a router is busy** even though they can see `deployment_status`. | `RouterOperationViewSet.permission_classes` | Viewers see the deployment badge only; the operations list and “busy” hints are gated on `routers.manage`. |
| 27 | **`POST tenant-memberships/` requires `tenant` in the body even for owners** (400 “This field is required.”), although the view then pins owners to their own tenant regardless of the value. *(Found in Phase 6.)* | `TenantMembershipSerializer` (`tenant` is a required PK field), `TenantMembershipViewSet.perform_create` | Team → Add member always sends `tenant: <principal.tenantId>`; `TenantMembershipWrite.tenant` is typed as required. | 28 | **Subscription checkout creates a pending `SubscriptionPayment` before contacting Paystack**, so a 503 (“Payment provider unavailable”) still returns a `reference` and leaves a pending row that only a later webhook/callback can settle. | 29 | **Payment recovery statuses are computed, not filterable.** `fulfillment_status` / `delivery_status` are serializer fields; `payment-recovery/` only filters on `status`/`plan`/`search`. | `PaymentRecoveryFilter` | “Needs attention” on the recovery board is a client-side narrowing of the current page (with an explicit “on this page” label). | 30 | **Credentials e-mail delivery is fire-and-forget**: `deliver/` returns `202` with a `pending` delivery; the result only shows up in `payment-deliveries/` later, and the transport (`error_code`, e.g. `smtp_timeout`) is the only diagnostic. | `PaymentRecoveryViewSet.deliver`, `PaymentDelivery` | The drawer polls `payment-deliveries/?payment=` every 5 s while any delivery is pending/sending and shows `error_code` as-is on failed rows. |

| 31 | **Changing your password revokes the current session too.** `SIMPLE_JWT.CHECK_REVOKE_TOKEN=True` embeds a password hash claim, so after `auth/change-password/` the very next request with the old access/refresh pair gets 401 “The user's password has been changed.” *(Observed live in Phase 6.)* | `config/settings.py` SIMPLE_JWT, `rest_framework_simplejwt.authentication` | Settings → Password re-authenticates with the new password immediately after a successful change; if that login fails the app signs out with an explanatory message instead of surfacing a confusing 401. |
| 32 | **No agent-scoped way to re-issue or re-send a sold voucher.** The agent history exposes the allocation only; there is no endpoint for an agent to trigger a credential delivery or view the customer’s copy. *(Phase 7.)* | `apps/agents/urls.py` (history/generate/wallet only) | The agent voucher list tells agents to contact the operator with the voucher username; managers use `/vouchers/:id` print or recovery “Email credentials”. Recommended fix: `POST agent/vouchers/{allocation}/deliver/` reusing the delivery pipeline. |
| 33 | **Public `buy/` does not scope `plan_id` to the storefront tenant.** Any active plan id is accepted regardless of the slug the customer came from (`InitializePaymentSerializer.plan_id` is a `PrimaryKeyRelatedField` over all active plans), so a crafted request can pay tenant A through tenant B’s page; the storefront only ever submits ids it listed for that slug. *(Phase 7, source review.)* | `apps/payments/serializers.py::InitializePaymentSerializer`, `apps/payments/views.py` (`tenant=plan.tenant`) | Checkout links carry `slug/checkout/planId` and the form only submits a plan present in that slug’s catalogue; the Paystack keys used are those of the plan’s tenant, so money still reaches the right operator. Recommended fix: accept `tenant_slug` (or nest `buy/` under `public/tenants/<slug>/`) and validate `plan.tenant`. |
| 34 | **No user lookup/search for administrators.** `tenant-memberships/` and `platform/staff-assignments/` take a numeric `user` id, but there is no endpoint that lists or searches accounts (by username/email), and list rows only carry ids (`user_display` exists on memberships only). | `TenantMembershipSerializer`, `StaffAssignmentSerializer`, `apps/accounts/urls.py` | Add-member and new-assignment dialogs take a **numeric user ID** with translated `does not exist` / account-kind errors; assignment rows show `User #id`. *(Phase 8.)* |
| 35 | **Staff invitations accept an empty `services` list** (`POST platform/staff-invitations/` with `services: []` → 201), producing an account that can accept the invite but reach nothing. | 36 | **Invitation tokens are never delivered by the backend** — `POST platform/staff-invitations/` returns the plaintext token exactly once (`Cache-Control: no-store`) and no e-mail is sent; an `Idempotency-Key` replay does return it again. | 37 | **`DELETE tenants/{id}/` is an immediate hard delete** cascading memberships, routers, plans, vouchers, agents and payment history — no soft delete, archive or dry run, and no confirmation token. | `TenantViewSet` (plain `ModelViewSet.destroy`), FK `on_delete=CASCADE` | Danger-zone dialog requires typing the slug; deactivation (`PATCH is_active=false`) is offered first as the reversible option; the platform tenant is excluded from both in the UI. *(Phase 8.)* |
| 38 | **Expired invitations still report `status: "pending"`**; expiry is only enforced at accept time, and the list has no `expired` filter. | `StaffInvitation.status` choices (`pending/accepted/revoked`), `accept` view compares `expires_at` | The staff page derives an *expired* badge client-side from `expires_at` (`invitationDisplayStatus`). *(Phase 8.)* |
| 39 | **Platform payment lists return tenant ids only** (`platform/payments/.tenant`, `wallet-payments/.tenant_id`, `subscription-payments/.tenant`, `audit-events/.tenant`) with no tenant name, and `wallet-payments` has no agent name either. | 40 | **Legacy vouchers keep a separate, unrecoverable password.** Vouchers issued before single-code credentials (and any manual voucher created with its own password) still have `password ≠ username`; the API never returns that password, so agents and the public result page cannot show it. | `Voucher.access_code` property (null when passwords differ), `VoucherSerializer` (`password` write-only) | The UI treats `access_code === null` as "username only": Sell result/agent list label such rows, the workspace voucher detail keeps the Print hint, and `/pay/result` never claims a code exists. | 41 | **Email delivery depends on a scheduled worker with no in-band health signal.** `process_payment_deliveries` must run every 30–60 s; if it does not, purchases pile up as `pending` deliveries and nobody is emailed, but the public callback cannot say so. | `apps/payments/management/commands/process_payment_deliveries.py`, `PaymentDelivery.status` | The result page shows the code itself, so the customer is never blocked by a stalled worker; the Recovery board exposes `pending` deliveries for operators. Non-gaps worth stating (so nobody "fixes" them client-side): amounts are kobo; vouchers can only be disabled once issued; router secrets are unreadable by design; ambiguous NAS addresses are excluded from sessions by design.
